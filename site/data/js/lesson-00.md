# Вводный 01. Архитектура сайтов: Статика, SPA (состояние) и Сервер

Суть урока:

- **Статика / SSG:** итоговая страница собирается заранее при сборке проекта.
- **SPA (в браузере):** страница строится на клиенте прямо из данных и состояния.
- **SSR / API (на сервере):** страница генерируется сервером в момент каждого запроса.

## 1. Три лагеря веб-разработки

[+] Чтобы не запутаться в десятках инструментов (HTML, Gulp, Vite, React, Next.js, Express), достаточно задать один вопрос: где и когда собирается HTML-страница, которую видит пользователь?

```js
/* Шпаргалка по трём лагерям веб-разработки:
   1. Заранее (до захода пользователя)  -> Статика / SSG (HTML, Pug, 11ty, VitePress, Astro)
   2. В браузере (на устройстве юзера)  -> SPA через состояние (Чистый JS, React, Vue)
   3. На сервере (в момент запроса)     -> SSR / Fullstack (Express+EJS, REST API, Next.js) */
```

[!] Для фронтенда без своего бэкенда есть два базовых пути: статика (готовые HTML-файлы) и SPA через состояние (`UI = render(state)`). Сервер появляется тогда, когда нужны аккаунты, пароли и общая база данных для разных устройств.

## 2. Лагерь 1: Статика (от ручного HTML до Astro)

[+] Статика — это «готовая книга на складе». Страницы уже собраны заранее и лежат на сервере как готовые `.html`-файлы.

```js
/* Эволюция статики (от простого к сложному):
   1. Ручной HTML + CSS           — отдельный .html на каждый экран (lesson-01.html...).
   2. Шаблонизаторы + SCSS        — Pug/EJS + SCSS + Gulp/Vite (общие header/footer склеиваются при сборке).
   3. Классические SSG (11ty)     — пишешь .md, генератор штампует готовые .html по одному шаблону.
   4. Документация (VitePress)    — статика + плавные переходы и поиск как в SPA.
   5. Острова (Astro)             — вся страница лёгкий HTML, а JS грузится точечно в «островках». */
```

[!] Главный минус ручной статики (ступень 1): при добавлении одной кнопки в шапку приходится редактировать все HTML-файлы вручную. Именно для решения этого придумали шаблонизаторы и SSG.

## 3. Лагерь 2: Подход через состояние — SPA (от чистого JS до React)

[+] SPA (Single Page Application) — это «конструктор в браузере». Сервер отдаёт одну пустую страницу (`index.html`) и данные (`.md`, `.json`), а JavaScript сам собирает интерфейс от объекта состояния (`state`).

```js
/* Главная формула подхода через состояние: UI = render(state) */
const state = {
  lessonId: 'lesson-01',
  theme: 'paper',
  isCheatMode: false,
};

/* Когда пользователь кликает, мы меняем НЕ экран напрямую, а state,
   после чего вызываем render(), который обновляет нужный кусок DOM: */
function setTheme(nextTheme) {
  state.theme = nextTheme;
  renderTheme();
}
```

```js
/* Эволюция подхода через состояние:
   1. Чистый JS в 1 файле          — state + ручной render() через innerHTML/createElement + live-server.
   2. Модульный JS + CDN (наш сайт)— import/export в браузере, localStorage, location.hash, marked + hljs.
   3. Чистый JS + Vite + TS        — сборщик для npm-пакетов, SCSS, минификации и проверки типов TypeScript.
   4. UI-фреймворки (React, Vue)   — описываешь шаблон от данных, а DOM обновляется автоматически.
   5. Сторы (Zustand/Redux/Query)  — общее состояние на десятки экранов и кэш запросов к API. */
```

[!] На чистом браузерном JS (без сборщика Vite) нельзя писать короткое `import { marked } from 'marked'` из `node_modules` — поэтому на минималках библиотеки подключают через CDN в `<head>` (с `defer`) или переходят на сборщик.

## 4. Лагерь 3: Серверный подход (от классического SSR до Next.js)

[+] Сервер (бэкенд) — это «кухня», где блюдо готовится по заказу в момент запроса. Сервер имеет доступ к базе данных, паролям и правам доступа.

```js
/* Эволюция серверного подхода:
   1. Классический SSR (Express + EJS, PHP) — сервер сам подставляет данные из БД в HTML и отдаёт страницу.
   2. REST API + SPA                        — сервер отдаёт только JSON, а SPA в браузере забирает его через fetch().
   3. БД + Авторизация (Postgres + Prisma)  — прогресс и заметки хранятся в облаке, а не только в localStorage.
   4. Fullstack-гибрид (Next.js, Nuxt)      — первый экран рендерит сервер (для скорости и SEO), дальше — SPA.
   5. Serverless / BaaS (Supabase, Workers) — готовая база и облачные функции без настройки своего VPS. */
```

[!] Обычный GitHub Pages умеет раздавать только статику и клиентский SPA (лагеря 1 и 2). Для серверного кода (лагерь 3) нужен хостинг с Node.js/Docker или облачный BaaS.

## 3 главные ловушки урока (чек-лист для повторения)

1. Путать SPA со статикой и пытаться скормить ИИ-боту ссылку вида `site/#js/lesson-25`: без выполнения JavaScript в `index.html` лежит пустой шаблон — ботам отдают чистые `.md`-файлы.

2. Пытаться импортировать `npm`-пакеты короткими именами (`import ... from 'marked'`) в браузере без сборщика (Vite/Webpack) — браузер не ищет модули в `node_modules`.

3. Начинать обучение сразу со сложных фреймворков (`React` / `Next.js`), не поняв базовую механику `UI = render(state)` на чистом JS — из-за этого магия фреймворка кажется непонятной при отладке багов.

## Вопросы для закрепления

**1. В чём принципиальная разница между обычным статическим сайтом (MPA) и приложением через состояние (SPA)?**

<details>
<summary>Показать ответ</summary>

В MPA каждый экран — отдельный готовый `.html`-файл, и при переходе браузер перезагружает всю страницу целиком. В SPA HTML-файл один (`index.html`), данные лежат отдельно, а JS при изменении `state` перерисовывает только нужную часть DOM без перезагрузки страницы.

</details>

**2. Почему в нашем проекте `site/` библиотеки `marked` и `highlight.js` подключены через CDN в `<head>`, а не через `npm`?**

<details>
<summary>Показать ответ</summary>

Потому что наш сайт работает напрямую в браузере без сборщика (`Vite` / `Webpack`). Чистый браузер не умеет искать пакеты в `node_modules` по короткому имени, а сама папка `node_modules` не попадает на GitHub Pages.

</details>

**3. Когда одного `localStorage` в SPA перестаёт хватать и возникает необходимость в сервере (Лагерь 3)?**

<details>
<summary>Показать ответ</summary>

Когда нужно хранить данные и прогресс в облаке для доступа с разных устройств (аккаунты и авторизация), прятать секретные ключи/логику на сервере или отдавать общие данные тысячам пользователей из базы данных.

</details>

<details>
<summary>Подсказка и решение</summary>

```js
'use strict';

const state = {
  lesson: 'Урок 00',
  isCheatMode: false,
};

function render() {
  /* Проекция состояния state в результат интерфейса */
  const modeLabel = state.isCheatMode ? 'ВКЛ' : 'ВЫКЛ';
  console.log(`${state.lesson} | Шпаргалка: ${modeLabel}`);
}

function toggleCheatMode() {
  /* Меняем состояние, а не «рисуем» напрямую в обход render */
  state.isCheatMode = !state.isCheatMode;
  render();
}

toggleCheatMode(); /* Урок 00 | Шпаргалка: ВКЛ */
toggleCheatMode(); /* Урок 00 | Шпаргалка: ВЫКЛ */
```
