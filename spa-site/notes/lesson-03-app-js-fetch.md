# Этап 1. Урок 3. Подробный разбор `app.js`: `fetch()`, `Response` и `innerHTML`

Суть урока: Весь первый этап держится на 15 строках `app.js` — находим контейнер `#content`, асинхронно запрашиваем `.md`-файл через два `await` (`Promise` → `Response` → поток байтов → строка) и вставляем разобранный HTML в страницу.

## 1. Построчный разбор `my-site/app.js`

[+] Разбор каждой строки с механикой под капотом:

```js
'use strict';
/* Включает строгий режим JS: запрещает случайное создание глобальных
   переменных без let/const и превращает тихие опечатки в явные ошибки */

const contentEl = document.getElementById('content');
/* Ищет в уже построенном DOM (спасибо defer) тег <article id="content">
   и сохраняет в contentEl ССЫЛКУ на этот реальный DOM-объект */

async function loadLesson() {
/* Ключевое слово async разрешает ставить await внутри функции.
   На паузу встанет только loadLesson, сам браузер и кнопки не зависнут */

  const response = await fetch('lesson-01.md');
  /* 1-й await: шлёт HTTP-запрос серверу и ждёт ТОЛЬКО заголовки ответа
     (объект Response со статусом 200 OK). Текст файла здесь ещё не прочитан */

  const markdown = await response.text();
  /* 2-й await: вычитывает весь поток байтов из ответа и собирает их
     в обычную JS-строку с Markdown. (Для JSON вместо .text() берут .json()) */

  contentEl.innerHTML = marked.parse(markdown);
  /* marked.parse() превращает строку Markdown в строку HTML-тегов.
     Запись в .innerHTML заставляет браузер распарсить теги в DOM-узлы
     и заменить старую надпись "Загрузка..." на готовый урок */
}

loadLesson();
/* Точка старта: вызывает функцию сразу после загрузки скрипта */
```

## 2. Что происходит под капотом на каждом миллисекундном шаге

[+] Вот что на самом деле лежит внутри памяти JS во время работы двух `await`:

```js
/* === ШАГ 1: Вызываем fetch() (до срабатывания await) === */
const promise1 = fetch('lesson-01.md');
/* Браузер отправил HTTP GET-запрос и в ту же миллисекунду вернул
   обещание-квитанцию: promise1 === Promise { <state>: "pending" } */

/* === ШАГ 2: Срабатывает первый await === */
const response = await promise1;
/* Функция встаёт на паузу (Event Loop свободен). Когда сервер прислал
   ЗАГОЛОВКИ ответа, функция просыпается и получает объект Response:
   response === Response {
     status: 200,
     ok: true,
     url: "http://127.0.0.1:8080/my-site/lesson-01.md",
     body: ReadableStream  <-- текст файла ещё течёт байтами по трубе!
   } */

/* === ШАГ 3: Вызываем response.text() (до второго await) === */
const promise2 = response.text();
/* Метод собирает все кусочки (чанки) байтов из потока ReadableStream и
   переводит их из UTF-8 в текст, возвращая promise2 === Promise { "pending" } */

/* === ШАГ 4: Срабатывает второй await === */
const markdown = await promise2;
/* Поток закрылся, теперь в markdown лежит обычная готовая строка:
   markdown === "# Урок 01. Тестовый конспект\n\nСуть урока: ..." */
```

## 3. Единый объект `Response`: его методы и одноразовый поток

[+] `await fetch(...)` **всегда** возвращает экземпляр одного и того же класса **`Response`** (а имя переменной может быть любым), поэтому к нему всегда применимы одинаковые методы под разные типы файлов:

```js
/* 1. Обычный текст (.md, .txt, .html) -> возвращает строку */
const text = await response.text();

/* 2. Данные (.json, ответы API) -> сразу парсит в JS-объект или массив */
const data = await response.json();

/* 3. Картинки, PDF, .docx -> возвращает бинарный файл Blob */
const file = await response.blob();
```

[!] **Два важных подвоха `Response`:**
- **Поток одноразовый:** нельзя вызвать на одном `response` сначала `await response.text()`, а потом `await response.json()` — будет ошибка `body stream already read`.
- **Ошибка `404` не ломает `fetch`:** если файла нет на сервере, `fetch` всё равно вернёт `Response` со статусом `404` и `response.ok === false`. Поэтому в реальных проектах проверяют `if (!response.ok) throw new Error(...)`.

## 4. Почему нужен `live-server` (`npm run my-site`) и не работает `file://`

[!] Если открыть `index.html` двойным кликом с диска, браузер заблокирует `fetch()` с локального диска политикой безопасности (**CORS**). Локальный сервер `live-server` отдаёт те же файлы по протоколу `http://127.0.0.1:8080`, и `fetch()` работает штатно.

## 3 главные ловушки урока (чек-лист для повторения)

1. Забыть второй `await` перед `response.text()`: в переменную `markdown` запишется не текст урока, а нераспакованный `Promise`, и `marked.parse()` упадёт.

2. Вызвать два метода чтения (`response.text()` и `response.json()`) на одном объекте `response`: поток `body` можно прочитать только один раз (`body stream already read`).

3. Ждать, что `fetch('missing.md')` сам выбросит ошибку при `404 Not Found` — нужно проверять `response.ok`.

## Вопросы для закрепления

**1. Почему `await fetch(...)` недостаточно для получения текста урока и нужен второй `await response.text()`?**

<details>
<summary>Показать ответ</summary>

Первый `await` дожидается только заголовков ответа от сервера (`Response`), когда тело файла ещё только течёт потоком байтов (`ReadableStream`). Второй `await` дожидается полного чтения этого потока и склейки байтов в строку.

</details>

**2. Чем отличается `response.text()` от `response.json()`?**

<details>
<summary>Показать ответ</summary>

`response.text()` возвращает содержимое ответа как обычную строку (для `.md` или `.html`), а `response.json()` сразу парсит текст через `JSON.parse()` и возвращает готовый JS-объект или массив.

</details>
